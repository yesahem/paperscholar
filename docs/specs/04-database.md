# 04 — Database

Postgres, accessed through Drizzle ORM from `packages/db`. The Drizzle schema in
TypeScript is the source of truth; the SQL below describes the intended result.

## 1. Connections

- The API connects through a **transaction-mode connection pooler**. Serverless instances
  open and drop connections constantly, and a direct connection per instance would exhaust
  Postgres.
- Driver: Bun's built-in `Bun.sql` with Drizzle's `bun-sql` adapter. Prepared statements
  are disabled (`prepare: false`), because transaction-mode poolers do not support them.
  Everything that talks to Postgres runs on Bun, so no Node driver is needed.
- One client per function instance, created at module scope and reused across warm
  invocations. Pool size per instance: 3.
- Migrations and seeds use a **direct** connection (`DATABASE_URL_DIRECT`), from CI or a
  developer machine, never from a request.
- The driver is imported in exactly one file (`packages/db/src/client.ts`).

## 2. Conventions

- Table and column names are `snake_case`. Table names are plural, except the tables
  Better Auth owns.
- Primary keys are UUIDv7 generated in the application, unless noted.
- Every table has `created_at timestamptz not null default now()`. Mutable tables also have
  `updated_at`.
- Enumerations are `text` columns with a `CHECK` constraint, mirrored by the zod enums in
  `packages/shared`. Postgres `ENUM` types are avoided because altering them is awkward.
- In user-data tables (`submissions`, `progress`, …), paper and problem IDs are plain
  `text` with no foreign key. A user's history must survive a paper being archived or a
  problem being retired.
- Foreign keys to `user` use `ON DELETE CASCADE`, so deleting an account removes its data.

## 3. Tables owned by Better Auth

`user`, `session`, `account`, `verification`. Their definitions are generated by the
Better Auth CLI into `packages/db/src/schema/auth.ts` and MUST NOT be edited by hand.
Extra columns on `user` are declared through Better Auth's configuration:

| Column     | Type                 | Purpose                         |
| ---------- | -------------------- | ------------------------------- |
| `username` | text, unique         | Public handle (username plugin) |
| `role`     | text, default `user` | `user`, `maintainer` or `admin` |

Application code reads `user` but writes to it only through Better Auth.

## 4a. What is not in the database

**Paper content is in object storage (Cloudflare R2), not here.** There are no `papers`
or `problems` tables. Papers, problems, descriptions, starters, solutions, tests, tracks,
quiz sets and courses are objects, laid out in spec 03 §2.

What the database keeps about content is **state only**:

- the advisory lock that serialises writes to `index.json` (no table): a transaction-scoped
  `pg_advisory_xact_lock(hashtext('content-index'))`, which works through transaction-mode
  poolers (`createAdvisoryLock` in `@repo/db`);
- the status of an edit awaiting verification:

```sql
create table content_candidates (
  id           uuid primary key,
  paper_id     text not null,
  status       text not null default 'pending'
                 check (status in ('pending','verifying','passed','failed','applied')),
  verification jsonb,                 -- result of each check
  created_by   text references "user"(id) on delete set null,
  created_at   timestamptz not null default now(),
  updated_at   timestamptz not null default now()
);
```

The edited files themselves are the object
`content/papers/<paperId>/candidates/<id>.json`;

- the pipeline's job state (§6).

Consequences for the tables below:

- Paper and problem IDs in user-data tables are plain text with no foreign key.
- A problem's difficulty and a paper's problem list, needed when recording a solve
  (§5.1), are read from the cached `index.json`, not from a table.
- `submissions.content_version` is the paper's version number at grading time.

## 4. Core tables (milestones 4–5)

```sql
create table profiles (
  user_id     text primary key references "user"(id) on delete cascade,
  bio         text check (char_length(bio) <= 280),
  avatar_key  text,
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now()
);

create table submissions (
  id              uuid primary key,
  user_id         text not null references "user"(id) on delete cascade,
  paper_id        text not null,
  problem_id      text not null,
  mode            text not null check (mode in ('run','submit')),
  code            text not null,
  status          text not null default 'queued'
                    check (status in ('queued','running','completed','error')),
  verdict         text,           -- null until finished; values in spec 02 §7
  tests_passed    integer,
  tests_total     integer,
  result          jsonb,          -- per-test results, see spec 07 §6
  duration_ms     integer,
  content_version text not null,
  created_at      timestamptz not null default now(),
  started_at      timestamptz,
  finished_at     timestamptz
);
create index submissions_user_recent   on submissions (user_id, created_at desc);
create index submissions_user_problem  on submissions (user_id, paper_id, problem_id, created_at desc);
create unique index submissions_one_in_flight
  on submissions (user_id) where status in ('queued','running');
create index submissions_in_flight_age
  on submissions (created_at) where status in ('queued','running');

create table progress (
  user_id             text not null references "user"(id) on delete cascade,
  paper_id            text not null,
  problem_id          text not null,
  difficulty          text not null,
  first_submission_id uuid references submissions(id) on delete set null,
  solved_at           timestamptz not null default now(),
  primary key (user_id, paper_id, problem_id)
);

create table paper_completions (
  user_id      text not null references "user"(id) on delete cascade,
  paper_id     text not null,
  completed_at timestamptz not null default now(),
  primary key (user_id, paper_id)
);

create table user_stats (
  user_id          text primary key references "user"(id) on delete cascade,
  problems_solved  integer not null default 0,
  easy_solved      integer not null default 0,
  medium_solved    integer not null default 0,
  hard_solved      integer not null default 0,
  papers_completed integer not null default 0,
  current_streak   integer not null default 0,
  longest_streak   integer not null default 0,
  last_active_day  date,
  last_solved_at   timestamptz
);
create index user_stats_by_solved on user_stats (problems_solved desc, last_solved_at asc, user_id);
create index user_stats_by_papers on user_stats (papers_completed desc, last_solved_at asc, user_id);
create index user_stats_by_recent on user_stats (last_solved_at desc nulls last, user_id);

create table daily_activity (
  user_id        text not null references "user"(id) on delete cascade,
  day            date not null,               -- UTC
  submissions    integer not null default 0,
  passed_submits integer not null default 0,
  new_solves     integer not null default 0,
  primary key (user_id, day)
);

create table follows (
  follower_id text not null references "user"(id) on delete cascade,
  followee_id text not null references "user"(id) on delete cascade,
  created_at  timestamptz not null default now(),
  primary key (follower_id, followee_id),
  check (follower_id <> followee_id)
);
create index follows_by_followee on follows (followee_id);

create table rate_limit_counters (
  key          text not null,
  window_start timestamptz not null,
  count        integer not null default 0,
  primary key (key, window_start)
);
```

Notes:

- `submissions_one_in_flight` enforces "one run at a time per user" in the database, so
  two simultaneous requests cannot both succeed.
- `user_stats` exists so the leaderboard is an index scan, not an aggregate over
  `progress` on every request.
- `daily_activity` backs the profile heatmap and streaks.
- The reference site's "friends" are one-directional adds with no acceptance step, which
  is a follow relationship. It is named `follows` here.

## 5. Invariants

### 5.1 Recording a solve

When a `submit`-mode submission finishes with verdict `passed`, the following happens in
**one transaction**:

1. Update the `submissions` row (status, verdict, result, timings).
2. `insert into progress ... on conflict do nothing returning *`.
3. If a row was returned (first solve of this problem):
   - increment `user_stats.problems_solved` and the matching difficulty counter; set
     `last_solved_at`;
   - if the user now has a `progress` row for every published problem of the paper,
     `insert into paper_completions ... on conflict do nothing` and, if inserted,
     increment `papers_completed`.
4. Upsert `daily_activity` for today: `submissions + 1`, `passed_submits + 1`, and
   `new_solves + 1` when step 3 applied.
5. Update the streak: if `last_active_day` is today, no change; if yesterday,
   `current_streak + 1`; otherwise `current_streak = 1`. Then set `last_active_day` to
   today and raise `longest_streak` if exceeded.

For any other finished submission, only steps 1 and the `submissions + 1` part of step 4
apply. A submission ending in `internal_error` does not touch `daily_activity`.

### 5.2 Other rules

- `progress` rows are never deleted or revoked by content changes.
- `paper_completions` rows are never revoked. `papers_completed` always equals the count of
  that user's rows.
- `user_stats` and `profiles` rows are created by a Better Auth after-create hook. The
  hook may not share the user-creation transaction, so writes to these tables are upserts
  and reads treat a missing row as all-zero / empty.
- Days and streaks use UTC. This is a simplification; per-user time zones are out of scope.
- A nightly job recomputes `user_stats` from `progress` and `paper_completions` for a
  sample of users and logs any drift. Counters are a cache of derivable truth.

## 6. Pipeline tables (milestone 6)

`ingestions`, `ingestion_steps` and `pipeline_tasks` are defined in spec 09 §15, next to
the pipeline that uses them. They hold status and bookkeeping only; everything the
pipeline generates is an object in storage.

There are no billing, subscription or purchase tables. The project has no payments.

## 8. Retention

| Data                             | Kept                                                           |
| -------------------------------- | -------------------------------------------------------------- |
| `submit`-mode submissions        | Indefinitely                                                   |
| `run`-mode submissions           | 30 days, then deleted by the cleanup job                       |
| `rate_limit_counters`            | 1 day                                                          |
| Ingestions, chunks, step history | Kept while the paper exists; deleted when a draft is discarded |
| Uploaded paper PDFs              | Kept while the ingestion exists; private bucket                |
| Finished `pipeline_tasks`        | 30 days                                                        |
| Sessions                         | Until expiry; expired rows deleted by the cleanup job          |

Account deletion removes the `user` row; cascades remove everything else. Object-storage
files (avatar, CVs) are deleted by the same service call.

## 9. Migrations

- Generated with `drizzle-kit generate` and committed. Never edited after merge.
- Applied by CI before the API is deployed (spec 11 §7).
- Every migration must be safe to run while the previous API version is still serving:
  add columns as nullable or with defaults; drop columns only one release after the code
  stops using them.
- `bun run db:seed` creates one admin, one maintainer, two ordinary users and a little
  progress, for local development and preview environments only.
